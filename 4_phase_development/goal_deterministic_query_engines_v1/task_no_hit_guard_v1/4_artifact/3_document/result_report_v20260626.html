T-031 no_hit_guard_v1 结果报告

生成时间: 2026-06-26 | 守卫版本: pxfquery-T-031 | 关联任务: T-013 (CAP-05)

1. 一句话结论

T-031 为 PxFquery 的 ForwardQuery 创建了一个可调阈值的无命中安全守卫，在 11/11 个无意义扰动名上成功返回 NOT_FOUND，同时保持 2/2 个真实基因查询（EGFR/A549、TP53/MCF7）的正常结果不受影响，解决了 T-013 能力合同 CAP-05 中登记的模糊匹配假阳性风险。

2. 项目背景

PxFquery 是一个 LINCS 驱动的扰动-功能生物信息学工作流。它的核心查询引擎 ForwardQuery 在收到用户输入的扰动名时，会依次尝试精确匹配、子串匹配、token-overlap 回退三个层级。问题出在第三个层级的回退策略上：只要发现任意一个 token 重叠（哪怕只有一个字符级 token），即接受为匹配，不设任何质量门槛。这意味着恶意或无意的无意义输入（如 egr 被误认为 EGR1、egfr_random 被误认为 EGFR）会产生看似可信但完全错误的查询结果。T-013 在 MVP 能力合同中明确记录此为 CAP-05 失败项，并将修复任务分配给本任务 T-031。

3. 核心结果

守卫的核心机制是两个可调参数。min_query_length_for_substring=4 要求子串匹配的查询名至少 4 个字符，在测试中阻断了 egr、bra、rab、akt 这 4 个假阳性来源。min_overlap_for_token_fallback=2 要求 token 回退时至少共享 2 个 token，阻断了 egfr_random、totally_egfr、something_braf、whatever-egfr 这 4 个假阳性来源。完全随机的输入（如 NONSENSE_ZZZ999、QWERTYASDFG）因在精确匹配和子串匹配两层均无命中且 token 重叠为零，被自然阻断。

正向控制方面，EGFR/A549 返回 found=True，含 20 个激活项和 20 个抑制项，匹配到 5 个观测；TP53/MCF7 返回 found=True，同样返回 20 个激活和 20 个抑制项，匹配到 2 个观测。结果与 T-029 基线一致，说明守卫的查询拦截仅发生在模糊回退阶段，对已确认的精确匹配路径无任何干扰。

4. 项目价值

对本项目而言，T-031 解决的不只是一个函数调用问题。CAP-05 的失败意味着整个 forward query 管线的结果可靠性缺乏基础保证——任何一个误输入的扰动名都可能生成一条看起来有效但实质错误的证据链，污染下游的 resolver 摘要、LLM 解释和最终的科学结论。守卫的存在将这类错误从"罕见但可能"变为"被机制阻断"。对后续任务而言，T-031-D-001（NoHitGuardForwardQuery）可以直接替换 T-024 的 ForwardQuery，无需等待 workflow 级重构。如果要做一个类比，这个守卫相当于 API 层的输入校验：它不增加新功能，但在所有用到 ForwardQuery 的地方自动提供了一层安全垫。

6. 后续使用方式

下游任务只需将 from pxfquery.forward import ForwardQuery 替换为 from pxfquery_T031_forward_no_hit_guard import NoHitGuardForwardQuery，然后 guard = NoHitGuardForwardQuery(adata) 即可。若需要更严格的匹配（例如接受更少的 token 重叠风险），可调高 min_overlap_for_token_fallback 至 3 或更高。若以后引入了一批真正以短字符命名的扰动（例如 2 字符基因符号），可将 min_query_length_for_substring 下调至 3 或 2，但建议同时评估假阳性风险。

7. 边界与风险

守卫不处理以下场景：细胞系名称的模糊匹配（与扰动名类似的问题，需独立评估）、resolver 层的语义歧义、LLM 摘要的准确性、以及 function_index 缺失导致的空结果（属于矩阵覆盖问题）。此外，当前阈值基于 A-005 矩阵的扰动名分布，若后续数据源 xpr_func_ad.h5ad 被替换或扩展，建议运行本任务的测试脚本验证阈值是否仍然合适。守卫未修改任何上游资产（T-024、T-026、T-029、T-021 均保持原状），因此不会引入版本冲突。
