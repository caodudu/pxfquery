T-025 resource_manifest_v1 — 成果报告

生成时间: 2026-06-26 | 任务 ID: T-025

为 T-021 标准资源包（19 个文件，323.47 MB）建立了正式的资源清单与配套文档，使这套资源可以被下游任务直接引用而无需重复发现。

1. 项目背景

PxFquery 项目在 T-021 阶段完成了标准资源的收集和验证，将散落在不同上游任务中的功能矩阵、查询索引和元数据表集中为一个 19 文件的标准化包（D-004）。但后续的使用者——无论是开发人员、测试脚本还是打包流程——都面临一个实际问题：拿到这个资源包之后，无法快速知道里面有什么、每个文件怎么用、格式是否一致。T-025 的任务就是解决这个"最后一公里"问题：为资源包配上索引。这不是一个数据生产任务，而是一个基础架构任务。它产生的不是数据，而是关于数据的元数据——一份 YAML 清单、一份 schema 摘要和一份使用手册。这三份文档共同构成 T-021 资源包的"使用说明书"，让后续任务可以零歧义地定位和加载任何一份文件。

2. 核心结果

任务产出的核心是一份 19 条目的 YAML 清单（pxfquery_T025_standard_resource_manifest_v20260623.yaml），每条记录包含该文件的标识符（SRM-001 至 SRM-019）、文件名、类别（matrix/index/metadata/description）、格式、角色描述、schema 关键信息（如 H5AD 的 obs 列名和 var 数量、JSON 的顶层键形状、CSV 的行数估计和关键列名）以及备注。配有两份 markdown 文档：schema 摘要按文件类别组织，列出每一类的通用结构（如三个 H5AD 共享相同的 7 列 obs 和 91 个 var，所有 JSON 索引的顶层键模式均在摘要中说明）；使用手册提供了 Python 加载代码片段（anndata 读 h5ad、json 读索引、pandas 读 csv），以及路径引用规则和验证清单。通过 Python 验证确认：清单中的 19 个文件名与磁盘完全一致，所有文件存在且非空，总大小误差 0.00%。

3. 项目价值

这份清单改变了 T-021 资源包的使用方式。在 T-025 之前，一个下游任务如果要使用 cp_func_ad.h5ad，需要自己翻阅 T-021 的验证记录来确认它的 obs 列名和 var 数量。在 T-025 之后，任何引用 T-021 资源的任务只需要加载这个清单 YAML，即可获得全部文件的 schema 元数据。这对后续的 T-026 到 T-030 开发任务尤其关键：它们不再需要在上游任务中搜索 schema 信息，而是从清单中直接获取。从项目管理角度看，这份清单也是 CyHex 任务图中第一个正式的资源配置文件——它使得 T-021/D-004 这个资产在任务图中有了一条明确的使用链路。未来打包发布时，package 脚本也可以直接解析这个 YAML 来确定需要 vendored 的文件列表，而不必人工维护。

5. 后续使用方式

清单的使用方式在 pxfquery_T025_usage_notes_v20260623.md 中有详细说明。核心原则是：清单是 T-021/D-004 的索引而非副本，所有文件路径都指向 T-021 任务下的原始位置，下游任务按需直接读取这些路径即可。如果在后续开发中发现清单中的某个条目与实际文件结构不符（例如 obs 列在版本更新后发生变化），正确的做法是更新清单 YAML 中的对应条目，而不是修改资源包中的文件。使用手册中还列出了五个硬规则，包括"清单中列出的 category 不可被下游任务重分类"和"每个文件的 role 描述应包含其扰动类型"等。

6. 边界与风险

本任务不涉及对资源包本身的验证或修改。清单中记录的 schema 信息（如 obs 列名、JSON 顶层键）来自 T-021 的验证结果，如果 T-021 的验证存在遗漏，这份清单也会继承同样的误差。清单中的总大小 323.47 MB 精确到小数点后两位，但不意味着所有文件在每次引用时都保持完全相同的字节——它对应的是 T-021 验证时刻的快照。五个已知不可读的 CMAP 上游 H5AD 文件未被纳入清单，这是正确的，但它们也意味着资源包覆盖的扰动类型不包括 CMAP 原始管道数据。对于需要引用原始 CMAP 数据的任务，需要在更早的上游任务中寻找。
