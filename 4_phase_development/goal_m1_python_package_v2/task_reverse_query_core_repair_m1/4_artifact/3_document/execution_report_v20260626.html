T-060 执行报告 — reverse_query_core_repair_m1

生成时间: 2026-06-26

任务意图

PxFquery 项目需要同时提供正向（扰动→功能）和反向（功能→候选扰动）两种查询能力。M1 里程碑中，T-042 已定义了完整的反向查询 API 合同与演示用例，但前一尝试 T-049 因缺少关键支撑数据而失败：T-043/T-046 选定的固定夹具资产中既不含抑制术语 HALLMARK_MYC_TARGETS_V1，也不含 A549 细胞系的表达数据行，且未提供可用的夹具包清单。T-060 的任务是在不修改已完成的上游工件（T-042、T-043、T-046）的前提下，创建一套任务本地的合成修复基质，并交付原本应由 T-049 提供的反向查询核心，使下游任务能够正常消费反向查询能力。

输入资产与依据

本次执行严格依赖已注册的上游资产作为输入：T-042 的 API 合同（A-001）和演示用例（A-002）作为反向查询接口与验收标准的权威来源；T-043 的资源清单与夹具包（A-003、A-004）和 T-046 的加载器实现（A-009）作为夹具格式与加载机制的参考；T-044 的包骨架（A-007、A-008）提供了包结构与元数据的起点。此外，T-047 的加载器硬化参考（A-013、A-014）和 T-045 的索引健康摘要（A-012）作为可选的实现背景。T-049 的完成报告（A-015）仅作为故障参考，不从中复用代码。

实际执行过程

第一步，从 A-001 和 A-002 中提取反向查询所需的 API 字段、JSON 输出结构、排序期望值以及无命中/错误行为的规格。第二步，检查 T-043/T-046 的夹具覆盖率，通过 A-011 的烟雾证据确认原始 xpr 夹具确实缺少 HALLMARK_MYC_TARGETS_V1 列和 A549 行，验证了此前的故障根因。第三步，在 4_artifact/2_persist/reverse_repair_fixture_m1_1/ 下创建合成修复基质，包含一个 15 个观测 × 9 个变量的 xpr 表达矩阵（h5ad 格式）和对应的修复清单 reverse_repair_manifest_m1_1.yaml，确保 HALLMARK_MYC_TARGETS_V1 和 A549 同时可用。

第四步，编写修复基质来源说明文档（reverse_repair_provenance_v20260624.md），明确区分哪些部分直接复制自前驱夹具侧车文件、哪些部分是合成新增的修复行。第五步，在 T-044 包骨架基础上实现反向查询核心代码，包含 func2pert 函数、确定性余弦排序（非有限分数过滤、同分按 cmap_name → cell_iname → sig_id 升序稳定断平）、CLI reverse 子命令以及完整的结构化错误/无命中处理（NoMatrixLoaded、ProgramNotFound、ContextNotFound、LowConfidenceResult、空目标反向无命中）。

第六步，在 pxfquery conda 环境中运行正面演示脚本和错误/无命中脚本，生成结构化 JSON 证据。对应命令为 generate_reverse_repair_fixture.py 和 run_reverse_evidence.py。第七步，通过重复查询验证排序可重复性，并执行 CLI 烟雾测试确认命令行入口正常工作。最后在 4_artifact/registry.yaml 中注册所有可复用输出，并生成 HTML 执行与结果报告。

关键判断与证据

一个关键的架构判断是：合成修复基质仅用于合同桥接，不得被视为原始 LINCS/CMAP 数据或生物学证据。该基质的每行均在来源说明中标注了合成标签，确保下游开发者不会误用其进行生物学解读。正面演示结果中，found: true，最佳候选为 THTPA（余弦相似度 1.0），排序列表在前 10 名内保持了稳定的候选顺序。无命中/错误测试覆盖了五种独立场景：未加载矩阵、程序术语未找到、生物学上下文未找到、低置信度结果以及空目标列表，全部返回了符合 T-042 合同的结构化 JSON 错误响应。

所有验收证据均已归档：正面演示 JSON（reverse_demo_evidence_v20260624.json）、错误/无命中 JSON（reverse_error_no_hit_evidence_v20260624.json）、排序得分表（reverse_ranking_evidence_v20260624.csv）以及 CLI 烟雾输出（reverse_cli_smoke_stdout_v20260624.json）。这些文件构成了下游消费方验证反向查询能力的直接依据。
