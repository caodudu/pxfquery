T-065 M1 vs Delivery Anchor Review 结果报告

一句话结论

M1 应被理解为 deterministic kernel/substrate，而不是完整 PxFquery algorithm package milestone；下一步应先做 M2 current-resource evidence-routing package，再做 M3 resolver/LLM user-facing milestone。

项目背景

M1 完成后，项目需要判断它是否已经可以作为完整算法包基础。这个判断不能只看“有没有包、能不能跑 demo”，因为 T-062/T-063/T-064 已经把项目真实交付范围定义为 package capability、resolver/LLM capability 和 evidence-routing capability 的组合。T-065 用这些锚点回看 M1，给出可追踪的能力状态。

核心结果

核心结果是 M1 被分类为 deterministic kernel/substrate。它部分支持 forward/reverse deterministic query、基础 context handling 和窄 no-hit behavior，但 resolver entry、LLM-assisted parsing、proxy routing、ambiguous/context-missing/transfer routes、route-aware metadata 和 standard resource compatibility 都没有充分证据。报告把每项能力标成 partial、downgraded、deferred-not-approved 或 evidence-insufficient，避免后续把缺口误读为完成。

项目价值

这个 review 的价值是给项目止损和定向。它承认 M1 的真实贡献：建立了可复用的确定性内核和包化底座；同时阻止项目把 M1 过度包装成完整算法包。这样后续规划可以更诚实：M2 应补当前标准资源和 evidence routing，M3 再补 resolver/LLM 用户入口，而不是在 M1 基础上直接声称完整交付。

后续使用方式

未来任务配置时，如果要引用 M1，应把它描述为 deterministic substrate，而不是 full algorithm package。M2 应聚焦 current-resource evidence routing 和标准资源兼容；M3 应聚焦 resolver/LLM user-facing behavior。任何声称 M1 已经覆盖 proxy/no-hit/transfer/LLM 的任务，都需要重新对照 T-065 的 capability matrix。

边界与风险

T-065 没有重新运行 M1，也没有修代码或补 benchmark。它只审查已登记证据。若后续有新验证、修复或补实现，必须通过新的 task 产出新证据，再更新对 milestone 的判断。
