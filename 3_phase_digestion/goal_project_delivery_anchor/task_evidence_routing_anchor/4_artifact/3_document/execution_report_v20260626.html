T-064 证据路由锚点执行报告

任务意图

PxFquery 的核心价值不只是从矩阵中查到扰动与功能的数值关系，更在于向用户解释"为什么这个结果可信"。前序任务已暴露出多处风险：no-hit 场景下模糊回退会产生假阳性命中（T-013 的 CAP-05），resolver 因索引命名问题被阻塞（CAP-07），LLM 辅助模式在 6/9 次测试中不稳定且单次响应耗时 167 秒（T-007 风险评估）。T-064 的任务就是针对这些已知缺陷，建立一套 evidence-routing 行为合同，明确规定每种查询结果属于 exact-hit、proxy-hit、no-hit、ambiguous-hit、context-missing 还是 transfer/suggestion，并且每种路由都必须携带可检查的元数据。没有这层锚点，后续 M3 实现可能会把模糊匹配伪装成精确结果，把代理命中当作完整证据，或者让 LLM 文案替代 matrix 数据。这个任务的交付物属于 specification 层面，不涉及代码实现，但它是所有后续实现必须引用的验收基准。

输入资产与依据

本次执行读取了 5 份前序任务登记资产（A-001 至 A-005），所有判断均来自这些已注册文档，没有扫描遗留代码目录或上游任务文件夹。T-007（A-001/A-005）提供了开发状态中 resolver 和 proxy 行为的设计意图、7/7 deterministic matrix 的验证结果、以及 LLM 稳定性与延迟风险。T-013（A-002）给出了两个关键失败证据：CAP-05 表明无阈值约束的 no-hit 模糊回退会产生假阳性，CAP-07 展示 resolver 因命名差异被功能索引阻塞的实际情况。T-021（A-003）列出了可供路由使用的标准资源集——3 个功能矩阵、10 个查询索引（包括重建后的 function_index.json）、以及 5 个元数据表——这些构成了路由定义中的具体引用对象。T-058（A-004）提供了 29 个 stress-test 场景及其 pass/fail/borderline 分类，是本次 stress-test 映射交付物的直接原料。

实际执行过程

执行分为五个阶段。第一阶段是整理前序证据中所有与路由相关的事实，包括 exact-hit 逻辑的验证状态、proxy 路由层级（扰动代理、细胞系代理、双向代理）、no-hit 假阳性风险、以及 LLM 模式的已知边界。确认六种路由类型都能从现有证据中获得有意义的定义。第二阶段撰写路由分类法文档（D-001），定义六个路由类型的决议路径、置信度规则，并为每个类型编写结构化的验收案例，共计 21 个案例。第三阶段撰写证据元数据合同（D-002），以 YAML 格式定义每次路由响应必须携带的 8 个字段（route_type、query_context、perturbation_resolution、function_response、confidence、proxy_chain、diagnostics、suggestions），并为每个字段规定类型、枚举值、路由类型约束，额外包含 LLM 角色限制（llm_fields）和代理阈值策略（threshold_policy）。第四阶段将 T-058 的 29 个 stress-test 场景逐一映射到路由类型，生成 CSV 映射表（D-003），每个场景标注主/次路由分配、预期行为、代理可能性、LLM 依赖关系、验收标准和实现说明。

关键判断与证据

本次执行中最关键的判断围绕 no-hit 和 proxy-hit 的透明度。no-hit 路由必须有显式相似度阈值守卫——药物成分使用 Tanimoto 系数 ≥0.40，基因成分使用余弦相似度 ≥0.50——低于阈值的查询必须返回 NO_HIT 而不能偷偷执行模糊回退，这是直接针对 CAP-05 失败的修复约束。proxy-hit 路由必须暴露完整的 proxy_chain 字段（例如"A549 → NCI-H226 via subtype neighbor"）和置信度等级，不允许把代理命中包装成 exact-hit 返回。LLM 在证据路由中的角色被限制为辅助功能：它可以辅助解析用户输入、生成自然语言摘要、在确定无证据时提供转移建议，但不能替代 matrix 或 index 数据作为查询证据来源。此外，确认 T-058 的 29 个场景中没有独立的 ambiguous-hit 和 transfer/suggestion 场景——这两类路由的验收案例（AC-012 至 AC-021）是从 no-hit、context-missing 等场景间接推导的，这是明确的未来测试缺口。

交付物清单

三项核心交付物均已写入并登记在 4_artifact/registry.yaml 中。D-001 是证据路由分类法文档，路径为 4_artifact/2_persist/evidence_routing_route_taxonomy_v20260625.md，包含六类路由定义和 21 个验收案例。D-002 是证据元数据合同，路径为 4_artifact/2_persist/evidence_routing_metadata_contract_v20260625.yaml，包含 8 个字段的完整架构定义、路由类型约束、LLM 角色限制和代理阈值策略。D-003 是 stress-test 锚点映射表，路径为 4_artifact/5_table/evidence_routing_stress_test_mapping_v20260625.csv，覆盖全部 29 个 T-058 场景。此外，两份 HTML 报告（R-001 和 R-002）也登记在 registry 中。

边界与未完成事项

T-064 是 specification-only 锚点任务，没有编写任何实现代码，没有运行压力测试，也没有验证 runtime 路径。T-021 虽然重建了 function_index.json，但该索引在 pxfquery 包 resolver 中的运行时路径对齐情况不在本次范围内验证。ambiguous-hit 和 transfer/suggestion 两类路由虽然在分类法和验收案例中有定义，但 T-058 未提供专门的测试场景来覆盖它们，这可能导致未来应力测试阶段发现额外的边界问题。后续 M3 或 stress-test milestone 在引用 T-064 的锚点定义时，应当根据自身实现范围补充缺失的测试场景，并将本文的三项交付物作为 must-reference 的验收输入。
