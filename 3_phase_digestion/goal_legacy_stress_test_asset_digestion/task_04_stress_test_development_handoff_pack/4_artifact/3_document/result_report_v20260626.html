结果报告：T-058 04_stress_test_development_handoff_pack

1. 一句话结论

T-058 将前序三个消化任务的输出——160 个压力测试资产编目、29 个测试场景和 65 项复用边界判断——综合为一套结构化的开发阶段交接文档，为 PxFquery 项目的压力测试里程碑提供了完整的证据基线、缺口清单和任务序列，是 legacy_stress_test_asset_digestion 目标的最终集成产物。

2. 项目背景

PxFquery 是一个在 macOS 上重建的历史生物信息学项目，面向 LINCS 项目中药物和基因诱导的功能程序查询。项目的核心使命是构建一个可工作的当前工作空间，将 Windows 时代遗留的代码、数据、报告和投稿策略转化为受控资产，支撑后续的软件开发、可重现分析和实际的投稿路径。在项目路线图中，压力测试里程碑是验证遗留资产能否在当前环境中正确运行的关键环节，而 T-058 所生成的交接包就是到达该里程碑的桥梁——它不做执行，而是明确告知执行者：什么是已知的、什么是可复用的、什么是需要改写的、什么是缺失的。T-007 的开发状态报告为整个交接提供了现实的锚点，防止建议脱离当前代码库的实际能力。

3. 核心结果

交接包的集成分析建立了清晰的证据层级。最强的可执行证据来自确定性矩阵测试（M-0291/M-0386），该测试在所有三个前序任务中被独立认定为回归基线的最佳起点。29 个测试场景中，12 个标记为 PASS（可直接运行），6 个预期为 FAIL（路径或数据依赖需修复），其余属于边缘条件或手动检查类别。10 份历史报告和设计文档被判定为可直接引用资产，无需任何修改即可作为验证证据或架构参考。11 个遗留脚本需要改写，但改写范围仅限于工作空间路径更新——核心查询逻辑和计算方法是完整的。优先级最高的缺口是 function_index.json 的缺失，该文件是反向查询功能的前置条件，必须由资产 M-0373 构建器重新生成。运行时数据进一步确认：hybrid_fast 模式（0.825 秒，稳定）是推荐的默认测试配置，而 always_llm 模式（167.3 秒，6/9 稳定）应仅在有明确 LLM 测试目标时使用。

4. 项目价值

本任务的核心价值在于将三条分散的分析线索整合为一个可操作的交接文档，消除了任务间的手动对照需求。此前，T-055、T-056、T-057 的成果分散在各自的任务目录中，负责压力测试里程碑的开发人员需要自行跨任务阅读、对齐和判断，效率低且易遗漏矛盾。T-058 的交接包通过绘制资产-场景交叉映射、标识复用就绪资产和编目优先级缺口，使得里程碑启动时可以直接进入执行层级的规划，而非重新进行消化阶段的分析。尤其重要的是，T-007 的对齐确保交接建议不超出当前开发状态的现实——例如，function_index.json 的重建被列为优先任务不是因为它在历史上重要，而是因为 T-007 确认当前代码库中该索引确实不可用且是反向查询的必要输入。这种证据锚定机制减少了未来执行中的意外障碍。

5. 交付物导读

交接包 D-001 位于 4_artifact/2_persist/stress_test_development_handoff_pack_v20260624.md，共 7 节。建议新读者从第一节（消化发现总结）开始获取全景，然后根据角色选择路径：如需选取测试场景，查阅第二节的资产-场景交叉映射；如仅需直接可用的验证证据，第三节列出 10 个可直接引用的资产；如负责代码移植，第四节给出 11 个需改写脚本的风险画像；如进行缺口填补，第五节按优先级排序了 19 项任务。D-002（recommended_stress_test_milestone_tasks_v20260624.md）定义了 7 项里程碑推荐任务（ST-M01 至 ST-M07），从工作区建立（ST-M01，依赖 T-007 D001）开始，经基线验证（ST-M02）、脚本移植（ST-M03）、缺口填补（ST-M04/ST-M05）、混合模式验证（ST-M06），到完整性审核（ST-M07）。每项任务包含依赖关系和证据依据，可直接用于里程碑规划。

6. 后续使用方式

压力测试里程碑的负责人应将 D-001 作为入口文档，从中获取资产清单、场景定义和复用状态，然后逐一执行 D-002 中的推荐任务序列。ST-M01 是所有后续任务的前置前提——需要先基于 T-007 的建议建立包工作区（可用 pip install -e . 或等效方式）。在脚本移植阶段（ST-M03），应优先处理本次分析中风险评分较低的资产（路径更新类），再逐步处理涉及数据依赖验证的中等风险资产。function_index.json 的填补（ST-M04）应在移植工作有基本进展后尽早启动，因为它是多个场景的执行依赖。在整个过程中，应定期对照 T-056 的 29 个场景清单进行覆盖率检查，确保每个场景都至少有一个对应的测试用例。交接包记录的 4 项诚实不确定性（Act-1 权限、套件变体、GSEA 链接、模式共存）应在确定测试方案时予以澄清，必要时可在 ST-M07 审核阶段附加专项分析。

7. 边界与风险

本任务有三项核心边界。第一，输出是消化阶段的文档交接，不是开发阶段的执行计划——里程碑负责人应根据自身的时间线和资源对推荐任务进行排期调整。第二，本任务未对前序分析质量进行二次验证，29 个场景和 65 项复用决策的准确性依赖于 T-055、T-056、T-057 的原始分析——如果其中某个前序任务存在分类错误或遗漏，该错误会原样传递到交接包中。第三，17 项 T-057 中标记为 historical_only 或 external_reference 的资产未被纳入推荐任务的作用范围，但如果后续需要查阅这些资产作为背景参考，它们的路径和描述在 D-001 的第五节有完整记录。最后，本任务涉及的所有判断均基于 2026-06-24 之前的资产状态，随着项目开发阶段的推进，代码库状态会变化，交接包中的某些建议（例如静默跳过标记）可能需要在未来的任务中更新。
