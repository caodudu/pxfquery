#### 3.1.1.1 文章（Article） 

搜索 EGFR 突变 + 肺癌 + 特定药物：

```bash
biomcp article search --gene EGFR --disease "lung cancer" --chemical erlotinib --limit 20
```


搜索 BRAF V600E 的各种表述（支持 | 分隔同义词）：
```bash
biomcp article search --gene BRAF --keyword "V600E|p.V600E|c.1799T>A"

```

排除预印本：
```bash
biomcp article search --gene BRAF --disease melanoma --no-preprints
```

获取单篇文章完整信息（PMID）：
```bash
biomcp article get 38768446 --full

```

#### 3.1.1.2 临床试验（Trial）更多示例

搜索乳腺癌 + CDK4/6 抑制剂 + 三期 + 招募中 + 美国：

```bash
biomcp trial search --condition "breast cancer" --intervention "CDK4/6 inhibitor" --phase PHASE3 

```

位置-based 搜索（例如波士顿附近癌症试验）：

```bash
biomcp trial search --condition cancer --latitude 42.3601 --longitude -71.0589 --distance 50

```

NCI 来源 + 特定突变要求：

```bash
biomcp trial search --condition melanoma --source nci --required-mutations "BRAF V600E" --allow-brain-mets true --api-key YOUR_NCI_KEY

```

获取试验特定部分（例如只看协议或地点）：

```bash
biomcp trial get NCT03006926 --include Protocol 

```

NCI 试验 + 高级过滤：

```bash
biomcp trial get NCT04280705 --source nci --api-key YOUR_KEY

```

#### 3.1.1.3 变异（Variant） 

搜索 TP53 致病变异 + 自动包含 OncoKB：
```bash
biomcp variant search --gene TP53 --significance pathogenic
```

搜索特定基因 + 包含 OncoKB（需 token）：
```bash
biomcp variant search --gene BRAF --include-oncokb
```

获取单个变异详细注释：
```bash

biomcp variant get "chr7:g.140453136A>T"

```


### 3.1.2 特性
**逻辑运算（Logical operations）**
意思：支持“并且”“或者”“不是”等逻辑组合，还能用括号分组，让查询更精确。
怎么做到的：

BioMCP 的核心搜索工具（search）使用一种叫 Unified Query Language (UQL) 的查询语法，直接支持布尔逻辑：
AND（并且）
OR（或者）
可以加括号 ( )

例子：
"gene:BRAF AND disease:melanoma" → BRAF 基因相关的黑色素瘤
"gene:EGFR AND (mutation:T790M OR mutation:C797S)" → EGFR 基因上有 T790M 或 C797S 突变的记录
"gene:TP53 AND variants.significance:pathogenic AND articles.date:>2023" → 2023 年后发表的、TP53 致病性变异的文献

当你直接在 Claude 等 AI 里用自然语言问复杂问题时，AI 助手会把你的话翻译成这种带逻辑的 UQL 格式，再调用 BioMCP 的工具去执行。


**跨领域关联（Cross-domain associations，如基因-疾病-试验）**
意思：你可以一句话同时问到基因 → 疾病 → 临床试验 → 文献 → 变异意义等多类信息，系统能自动把它们关联起来，而不是让你分别去查好几个数据库。
怎么做到的：

BioMCP 本身集成了多个权威数据源（PubMed、ClinicalTrials.gov、cBioPortal、MyVariant.info、OncoKB、NCI 等），这些源之间本来就有 ID 映射和关联关系。
当你用基因名搜索文章时，默认会自动带上 cBioPortal 的癌症类型突变频率总结（include_cbioportal=True）。
搜索变异时会自动拉 OncoKB 的临床意义解释，并关联到相关疾病/试验。
最关键的是 think 工具（顺序思考工具）：它让 AI 助手可以分步推理，比如：
先查基因 BRAF 在黑色素瘤中的突变频率
再查有哪些针对这些突变的临床试验
最后总结相关最新文献
→ 整个过程保持上下文，自动串联跨领域数据。

这种“关系发现”（cross-domain relationship discovery）是 BioMCP 设计的核心卖点之一，靠的就是工具链的组合 + 数据源的深度整合。


**自动处理同义词（Automatic synonym expansion）**
意思：你写“肺癌”，系统会自动理解它等同于“lung cancer”、“非小细胞肺癌”、“NSCLC”等各种说法，甚至包括缩写和拉丁学名。
怎么做到的：

在搜索临床试验（trial search）时，默认开启 expand_synonyms=True，会调用 MyDisease.info 等服务自动把疾病名展开成同义词集合，然后用这些词去匹配数据库。
基因、药物、疾病等实体都有专门的 getter 工具（gene_getter、disease_getter、drug_getter），这些工具本身就会返回标准定义 + 所有常用同义词列表。
文章/文献搜索时，也会把常见的变异写法（比如 V600E、p.V600E、c.1799T>A）视为等价，自动或手动支持多写法匹配。

例子：你问“GIST 的靶向药有哪些？”，系统会自动扩展成“gastrointestinal stromal tumor”、“GI stromal tumor”等，再去查。

BioMCP 本身不做“智能纠错”或“模糊匹配拼写错误”，它的同义词能力主要靠后端权威本体（ontology）和特定参数开关来实现，而不是像 ChatGPT 那样靠大模型的常识去猜。核心来源包括：

MyDisease.info（疾病）→ 最强的地方在这里
这个服务基于 MONDO、DO、NCIt 等多个疾病本体
当你输入一个疾病名（如“肺癌”“GIST”“黑素瘤”），它会先把输入映射到标准 ID（CUI），然后自动拉出所有官方同义词列表
示例：
输入 “GIST” → 自动扩展为 “gastrointestinal stromal tumor”“GI stromal tumor”“胃肠道间质瘤”等几十个同义词/翻译
输入 “乳腺癌” → 扩展为 “breast cancer”“mammary carcinoma”等

临床试验搜索（trial search） 默认开启 expand_synonyms=True，所以即使你说“胃癌晚期”，它也会尽量扩展到 “gastric cancer”“stomach cancer advanced”等去查 ClinicalTrials.gov

基因和变异：靠 MyVariant.info + PubTator3
基因名比较严格，通常需要标准 HGNC 符号（如 BRAF、EGFR），但支持常见别名/历史名
变异写法很灵活：支持 “V600E”“p.V600E”“c.1799T>A”“BRAF V600E”等多种写法同时搜索（用 | 分隔或 OR 逻辑）

NCI 工具（癌症相关疾病/干预）
有明确的 include_synonyms=True（默认开）或 synonyms 参数
NCI 的词汇表本身就包含大量同义词，所以输入 “melanoma” 或 “黑色素瘤” 都能匹配

文献搜索（PubMed/PubTator3）
PubTator3 本身有强大的实体识别和标准化能力（NER + 链接到标准 ID）
所以即使文章里写的是“non-small cell lung carcinoma”“NSCLC”“肺腺癌”等，搜索“肺癌”时也能被匹配到（因为后台做了规范化）

## 4.1 fastmcp
https://gofastmcp.com/getting-started/welcome
https://github.com/jlowin/fastmcp


MCP让您能够为智能体提供对工具和数据的访问。但构建一个有效的MCP服务器比看起来更困难。

给智能体太多东西——数百个工具、冗长的响应——它会不堪重负。给它太少,它又无法完成工作。协议本身很复杂,包含多层序列化、验证和错误处理,而这些都与您的业务逻辑无关。而且规范不断演进;上个月有效的方法可能已经需要更新。

真正的挑战不是实现协议,而是在正确的时间提供正确的信息。

这就是FastMCP解决的问题——也是它成为标准的原因。FastMCP 1.0于2024年被纳入官方MCP SDK。如今,这个持续维护的独立项目每天下载量达到一百万次,某个版本的FastMCP为所有语言中70%的MCP服务器提供支持。

该框架建立在三个抽象概念之上,这些概念映射到您实际需要做出的决策:

- 组件是您暴露的内容:工具、资源和提示。包装一个Python函数,FastMCP会处理模式、验证和文档。
- 提供者是组件的来源:装饰函数、磁盘上的文件、OpenAPI规范、远程服务器——您的逻辑可以存在于任何地方。
- 转换塑造客户端看到的内容:命名空间、筛选、授权、版本控制。同一个服务器可以向不同的用户呈现不同的内容。

这些元素可以完美组合,因此复杂的模式不需要复杂的代码。而且由于FastMCP对细节有明确的主张,如序列化、错误处理和协议合规性,最佳实践就是阻力最小的路径。您专注于自己的逻辑;MCP部分自然就能正常工作。

快速行动,创造价值。


官方 MCP SDK 的做法（繁琐）
你需要做 4 件事：

写函数：写查询数据库的代码
写说明书：手动告诉 AI 这个函数叫什么名字、需要什么参数、每个参数是什么类型
写调用逻辑：AI 想用这个函数时，你要写代码接收 AI 的请求、解析参数、调用你的函数
写返回逻辑：把结果格式化后返回给 AI
FastMCP 的做法（简洁）
你只需要做 1 件事：

写函数 + 加一个装饰器：在函数上面写 @mcp.tool()，其他的（说明书、调用、返回）全自动完成




使用官方 MCP SDK（更底层的实现）
```python
from mcp import Server
from mcp.types import Tool, TextContent

# 创建服务器实例
server = Server("my-server")

# 需要手动定义工具的元数据
@server.list_tools()
async def list_tools():
    return [
        Tool(
            name="add",
            description="Add two numbers",
            inputSchema={
                "type": "object",
                "properties": {
                    "a": {"type": "number"},
                    "b": {"type": "number"}
                },
                "required": ["a", "b"]
            }
        )
    ]

# 需要手动处理工具调用
@server.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "add":
        result = arguments["a"] + arguments["b"]
        return [TextContent(type="text", text=str(result))]
```

使用 FastMCP（高层封装）


```python
from fastmcp import FastMCP

# 创建服务器实例
mcp = FastMCP("my-server")

# 直接用装饰器，自动从函数签名和 docstring 生成元数据
@mcp.tool()
def add(a: float, b: float) -> float:
    """Add two numbers"""
    return a + b
```
