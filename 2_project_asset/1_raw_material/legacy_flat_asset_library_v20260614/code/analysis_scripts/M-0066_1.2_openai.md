# 2. 介绍
openai sdk 是 OpenAI 官方提供的一套软件开发工具包，目的是简化与 OpenAI API 的交互流程。
通过这个 SDK，开发者可以用熟悉的编程语言（例如 Python、Node.js 等）方便地调用 OpenAI 的各项服务，如自然语言处理、文本生成、图像生成等。
SDK 封装了底层的 HTTP 请求，提供了更友好的接口和错误处理机制，
帮助开发者快速构建基于 AI 的应用程序，同时也支持异步操作、自动重试等高级功能。


# 3. 使用

## 3.1 openai 官方标准openai.ChatCompletio

之前用于生成文本的标准(无限期支持)是Chat Completions API。您可以使用该API通过以下代码从模型生成文本。

openai.ChatCompletion 的作用：
- 聊天对话：ChatCompletion API 主要用于创建和管理与 OpenAI 模型的对话，支持连续的对话上下文。你可以提供一系列的用户消息和模型的回复，并获取模型的最新回应。
- 对话历史管理：每次请求时，你都可以提供一个对话历史（消息列表），模型会根据这些历史对话进行推理，从而生成相关的回复。这使得对话可以持续进行，而不是每次都从头开始。
- 多轮对话：可以进行多轮交互，模型会理解并基于之前的对话上下文生成回答，而不仅仅是单一的查询和响应。


```python
import openai
# 设置 API 密钥
openai.api_key = "你的API密钥"
# 调用 Chat Completions API
response = openai.ChatCompletion.create(
   model="gpt-4",
   messages=[
       {"role": "system", "content": "你是一个友好的助手。"},
       {"role": "user", "content": "如何检查一个 Python 对象是否是某个类的实例？"}
   ]
)
# 输出生成的内容
print(response['choices'][0]['message']['content'])
```

## 3.3 连续交互
需要手动管理，OpenAI SDK 不会自动处理多轮对话的上下文。

### 3.3.1 原理
1. **每次新的输入都会包含完整的历史对话**
```
第1轮：[系统提示 + 用户消息1] → 模型输出1
第2轮：[系统提示 + 用户消息1 + 模型输出1 + 用户消息2] → 模型输出2
第3轮：[系统提示 + 用户消息1 + 模型输出1 + 用户消息2 + 模型输出2 + 用户消息3] → 模型输出3
```

所以越早的对话内容，确实会被重复输入越多次。
因为 LLM 本身是无状态的：
模型没有"记忆"功能
每次调用都是独立的推理过程
必须通过输入完整上下文来"告诉"模型之前发生了什么


2. **成本平方增长**
随着对话轮数的增加，总的 token 消耗会 以平方的形式增长。

假设每轮对话的输入和输出都是 W 个 token，进行 k 轮对话：
调用token 不是 W * k。 而是 W (1+k) * k/2
假设每轮对话 1000 tokens，对话 10 轮：
直觉认为：1000 × 10 = 10,000 tokens
实际消耗：1000 × (1+2+3+...+10) = 1000 × 55 = 55,000 tokens
差了 5.5 倍！

3. **标准过程**
初始化对话：对话从一个系统消息开始，设定模型的角色是一个“有帮助的助手”，然后是用户的第一条消息。
连续交互：每次对话后，模型的回答会被添加到 messages 列表中。之后，新的用户输入会基于整个对话历史（包括之前的用户输入和助手回复）发送给模型。
对话上下文：每一轮的对话中，模型都会利用整个 messages 列表中的内容来生成新的回复，确保连续性和上下文的连贯性。

在 OpenAI 的 API 中，每次请求都会生成一个新的回复，而不是基于交互的顺序（即第一轮回复、第二轮回复、第三轮回复）返回不同的索引。每次你向模型发送请求时，它会根据输入的对话上下文生成一个新的回复。所以即使是多轮对话，每次返回的回复都是 新的生成结果，而 choices[0] 代表了这一轮生成的第一个结果。

对话上下文是如何保存的？
在多轮交互中，整个对话（包括用户和模型的消息）都会被作为输入传递给 API。模型会根据整个对话的上下文生成适当的回复，但是每次请求都会重新生成一个新的回复。

4. **应对策略**
token 数量递增：确实，随着对话的进行，messages 中的内容会增加，导致 token 数量递增。
超长对话的挑战：当对话历史过长时，可能会导致请求超过最大 token 限制，影响后续的模型调用。
常见的解决方式：通过限制对话历史的长度、使用 system 消息提供背景信息和截断冗余内容等方式来有效管理 token 数量。


限制对话轮数（比如只保留最近 10 轮）
定期清理上下文
使用摘要压缩历史
考虑使用向量数据库存储历史，按需检索关键信息



常见做法：三层记忆（最实用）
短期窗口（Recent window）
只保留最近 N 轮原文（比如最近 10～30 条 message），保证“正在聊的事”不会断。

长期摘要（Running summary / Compression）
把更早的内容压缩成一段“运行摘要”，每隔几轮或超过阈值就更新一次。
OpenAI 的 cookbook 里把这类操作叫 trimming + compression，并明确这是为了控制上下文、降低成本并减少“上下文中毒”。

检索增强（RAG over history / docs）
把更早的聊天记录按块（chunk）存到向量库或其他检索系统里；每次新请求来时，用当前用户问题做查询，只取回最相关的几块拼进 prompt。OpenAI 的“Building agents”里也把这种“按需检索再喂给模型”的套路定义为 RAG。



### 3.3.2 示例
```python
import openai

# 设置 API 密钥
openai.api_key = 'your-api-key'

# 初始化对话
messages = [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "Hello! Can you help me?"}

# 第一次请求模型回复

    model="gpt-4",  # 使用 GPT-4 模型

# 第二次请求模型回复
response = openai.ChatCompletion.create(
    model="gpt-4",
    messages=messages
)

# 获取并打印第二次的模型回复
assistant_reply = response['choices'][0]['message']['content']
print("Assistant:", assistant_reply)

# 将模型的回复添加到消息列表中
messages.append({"role": "assistant", "content": assistant_reply})

# 添加更多的对话
messages.append({"role": "user", "content": "Can you recommend a good restaurant?"})

# 第三次请求模型回复
response = openai.ChatCompletion.create(
    model="gpt-4",
    messages=messages
)

# 获取并打印第三次的模型回复
```

## 3.4 函数定义调用

1. 工具定义：我们创建了一个 get_weather 函数，它接收城市名，并通过 OpenWeatherMap API 获取天气信息。
2. 工具注册：我们在 tools 数组中定义了工具，指定工具的名称 get_weather，并描述了它的功能（获取天气信息）。这些工具信息会传给 OpenAI 模型。
3. 请求体：openai.ChatCompletion.create 被用来生成聊天模型的请求，我们在 messages 中提供了用户询问天气的问题，模型将理解并调用 get_weather 工具。
4. 响应：当 OpenAI 模型处理完请求后，它会返回包含天气信息的结果。


```python
import openai
import requests

# 假设你已经注册并获得了 OpenAI API key
openai.api_key = "your-openai-api-key"

# 自定义工具（函数）示例：从某个天气 API 获取天气信息
def get_weather(city):
    api_key = "your-weather-api-key"
    url = f"http://api.openweathermap.org/data/2.5/weather?q={city}&appid={api_key}"
    response = requests.get(url)
    weather_data = response.json()
    
    # 处理天气数据，返回一个简化的结果
    if response.status_code == 200:
        return f"The current weather in {city} is {weather_data['weather'][0]['description']} with a temperature of {weather_data['main']['temp']}°C."
    else:
        return "Sorry, I couldn't retrieve the weather data."

# 在 OpenAI API 请求中传入工具
tools = [
    {
        "name": "get_weather",  # 工具的名字，必须与定义的函数名称匹配
        "description": "Fetches current weather information for a city.",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {
                    "type": "string",
                    "description": "Name of the city"
                }
            }
        }
    }
]

# 构造请求体
response = openai.ChatCompletion.create(
  model="gpt-4",  # 使用 GPT-4 模型
  messages=[
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "What's the weather like in New York?"}
  ],
  tools=tools
)

# 输出响应
print(response)

```

## 3.5 结构化输出 response_format 参数
OpenAI 官方 API 支持让模型严格输出特定格式，不再靠 prompt 提示那种不可靠的方式。
除了在REST API中支持JSON Schema之外,OpenAI的Python和JavaScript SDK还可以分别使用Pydantic和Zod轻松定义对象架构。

**方法 A：简单 JSON 模式**
```python
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "user", "content": "提取这段文字的关键信息：小明今年18岁，住在北京"}
    ],
    response_format={"type": "json_object"}  # 强制返回 JSON
)

print(response.choices[0].message.content)
# 输出：{"name": "小明", "age": 18, "city": "北京"}

```
注意：使用时需要在 prompt 里提到 "JSON" 关键词。


**方法 B：JSON Schema（严格模式）**
使用 JSON Schema 定义精确结构：

```python
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o-2024-08-06",  # 必须是支持的模型
    messages=[
        {"role": "user", "content": "提取：小明今年18岁，住在北京"}
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "person_info",
            "strict": True,  # 严格模式
            "schema": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "age": {"type": "integer"},
                    "city": {"type": "string"}
                },
                "required": ["name", "age", "city"],
                "additionalProperties": False
            }
        }
    }
)

print(response.choices[0].message.content)
# 保证返回：{"name": "小明", "age": 18, "city": "北京"}
```

**方法 C：使用 Pydantic（最优雅）**
Pydantic 则是一个 数据验证库，它不仅支持 typing 模块中的类型注解，还会在 运行时验证 数据的类型和结构。
使用 Pydantic，你不仅仅是声明类型，它会在数据实例化时，自动验证字段是否符合指定的类型，并进行必要的类型转换（例如，将字符串 "123" 转换为整数 123）。
如果传入的数据不符合预期，Pydantic 会抛出详细的错误信息，告诉你哪里出了问题。


```python
from openai import OpenAI
from pydantic import BaseModel

client = OpenAI()

class CalendarEvent(BaseModel):
    name: str
    date: str
    participants: list[str]

response = client.responses.parse(
    model="gpt-4o-2024-08-06",
    input=[
        {"role": "system", "content": "Extract the event information."},
        {
            "role": "user",
            "content": "Alice and Bob are going to a science fair on Friday.",
        },
    ],
    text_format=CalendarEvent,
)

event = response.output_parsed
```

## 4.2. messages
说明：这是模型输入的对话内容，构成了与模型的交互历史。每个消息都有一个 role 和 content 字段：
- role：消息的角色，可以是 "system"、"user" 或 "assistant"。
  - **system**：设置模型的行为或限制，如：你是一个有用的助手。
  - **user**：用户输入的内容，模型需要基于这些内容生成回答。
  - **assistant**：模型之前的回答内容，帮助模型理解对话上下文。
- content：该消息的具体内容。可以是任何文本。
用法：你传递给模型的对话历史通常是一个列表，最新的消息会加在列表的末尾。
系统消息可以用来指导模型行为，用户消息则是模型需要回应的内容。


在代码中你只需要设置 user 角色
你只需要设置 user 角色来传递用户的提问或请求。
然后，模型会自动生成 assistant 角色的回应。
所以，实际上你并不需要手动去设置 assistant 角色。只要你向模型传递了 user 角色的消息，模型就会自动生成 assistant 角色的消息作为回应。

```shell
In [9]: response.choices[0].message.role
Out[9]: 'assistant'
```

## 4.3. temperature
说明：控制输出的随机性，值的范围通常是 0.0 到 2.0。
0.0：最确定的答案，模型生成的内容是确定性的，通常比较保守。
1.0：标准的平衡输出，既能生成合理的内容，也有一定的创造性。
2.0：非常创意，输出可能更加多样且不确定。
用法：适用于需要创意的任务（例如写作、创意写作、头脑风暴等），如果想要生成更精确和一致的内容，可以将其调低。

## 4.4. max_tokens
说明：限制生成文本的最大 token 数量（包括输入和输出）。每个 token 通常对应一个词或一个字。
例如，如果 max_tokens=100，那么生成的内容（包括用户的输入）不会超过100个 token。
用法：通常用于控制返回结果的长度。如果你只想要简短的回答，可以设置一个较低的 max_tokens 值。

## 4.5. top_p
说明：与 temperature 配合使用，控制模型生成内容时的候选词的选择范围。值的范围是 0 到 1。
1.0：默认行为，模型生成的词汇来自所有可能的选项。
0.0：模型只会选择概率最高的词汇。
用法：top_p 控制着词汇选择的“多样性”，如果想要更加保守和一致的输出，可以将 top_p 调低。通常，top_p 和 temperature 组合使用，可以调整生成的创意和质量。

## 4.6. frequency_penalty
说明：控制模型生成内容时的重复频率。值的范围是 -2.0 到 2.0。
0.0：没有惩罚，生成的内容可以有一定程度的重复。
2.0：最大惩罚，模型会尽量避免重复相同的词或短语。
用法：如果你希望模型的回答更丰富，避免同样的短语重复出现，可以设置较高的 frequency_penalty。

## 4.7. presence_penalty
说明：与 frequency_penalty 类似，但 presence_penalty 控制的是模型是否倾向于讨论新的话题或概念。

0.0：没有惩罚，模型会生成相对一致的内容。
2.0：最大惩罚，模型会尽量不重复之前已经提到的概念。

用法：如果你希望模型更有创意，提到新的内容，可以调高 presence_penalty。

## 4.8. stream
说明：是否开启流式返回输出。设置为 True 时，模型会逐步返回生成的文本，而不是一次性返回完整的响应。
用法：流式返回适用于实时交互的应用，如聊天机器人。如果不需要实时流式输出，通常设置为 False。


# 5. 其他功能
## 5.1 stream response 流式响应
OpenAI 的 stream response（流式响应）是指模型生成的文本逐字逐句实时返回，而不是等全部生成完才一次性返回。

两种响应模式对比
非流式（默认）
```python
response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "讲个故事"}],
    stream=False  # 默认
)
# 等待 5 秒...
print(response.choices[0].message.content)  # 一次性输出完整故事
```

流式
```python
response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "讲个故事"}],
    stream=True  # 启用流式
)

for chunk in response:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end='')  # 逐字输出
```
用户体验差异
非流式：

```css
[等待...]
[等待...]
[等待...]
从前有一个勇敢的骑士，他踏上了寻找宝藏的旅程...（完整故事一次性出现）
```
流式：
```
从（立即显示）
前（0.1秒后）
有（0.1秒后）
一（0.1秒后）
个...（持续输出）
```

主要优势
更好的用户体验 - 类似打字效果，感觉更快
降低感知延迟 - 用户立即看到响应，而不是干等
适合长文本 - 生成长篇内容时不会让用户等太久
可提前终止 - 如果用户不满意，可以中途取消
技术实现
使用 Server-Sent Events (SSE) 协议
每个 chunk 包含少量新生成的 token
HTTP 连接保持打开状态直到生成完成
通常每个 chunk 包含几个字符或一个词
实际应用场景
✅ 适合用流式：

聊天机器人界面
长文本生成（文章、代码、故事）
需要即时反馈的场景
❌ 不需要流式：

后台批处理任务
API 集成（直接用结果）
需要完整响应后再处理的场景

## 5.2 服务器自动重建上下文

OpenAI 确实推出了 Responses API，支持 previous_response_id 来链接对话111719：

```python
# 第1轮
response1 = client.responses.create(
    model="gpt-4o",
    input=[{"role": "user", "content": "Hello"}]
)

# 第2轮 - 使用 previous_response_id
response2 = client.responses.create(
    model="gpt-4o",
    previous_response_id=response1.id,  # 关键参数
    input=[{"role": "user", "content": "What did I say?"}]
)
```

工作原理
OpenAI 在服务端存储响应对象（默认 30 天）16
你只需传入新的用户消息 + 上一轮的 response ID
服务端自动重建完整上下文
重要限制
1. Token 计费不变
即使使用 previous_response_id，所有历史 token 仍然按输入 token 计费11。所以：
✅ 减少了网络传输和代码复杂度
❌ 不能减少成本（依然是 O(k²) 增长）
2. 存储时限
响应对象默认保存 30 天16
超时后无法通过 ID 引用
3. API 版本
这是较新的 API，可能需要更新 SDK 版本
